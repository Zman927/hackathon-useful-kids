# 브랜치 전략

## 표준 전략

| 브랜치 | 역할 |
|---|---|
| `main` | 항상 동작하는 상태. 시연·제출에 쓰이는 브랜치 |
| `develop` | 다음 통합 대상 기능들이 먼저 모이는 브랜치 |
| `feature/*` | 기능 단위 작업 브랜치 (예: `feature/rental-approve`) |
| `fix/*` | 버그 수정 브랜치 |
| `docs/*` | 문서 전용 브랜치 |

기능 브랜치는 `develop`에서 분기해 `develop`으로 머지하고, `develop`이 안정되면 `main`으로 머지하는 것이 정석이다.

## 이번 해커톤에서의 실제 적용

팀이 3명, 기간이 1.5일이라 `develop` 통합 브랜치를 별도로 두면 조율 비용이 실익보다 크다고 판단해 단순화한다.

| 브랜치 | 역할 |
|---|---|
| `main` | 통합 브랜치. `develop` 없이 바로 이 브랜치로 머지 |
| `frontend` | 프론트엔드 담당자의 작업 브랜치 |
| `backend` | 백엔드 담당자의 작업 브랜치 |

- 각자 자기 브랜치에서 작업하고, 기능이 동작하는 상태가 되면 `main`으로 머지한다.
- 기능이 더 잘게 쪼개져야 할 만큼 커지면 그때 `feature/*` 세부 브랜치로 내려간다 (예: `frontend` 브랜치 안에서 `feature/admin-dashboard`).
- `main`은 항상 시연 가능한 상태를 유지한다 — 깨진 상태로 오래 두지 않는다.

규모가 커지면 위 표준 전략(`develop` 포함)으로 전환할 수 있는 구조다.
